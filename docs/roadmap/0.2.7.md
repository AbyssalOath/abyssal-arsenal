# 0.2.7 plan: Panopticon NAC

**Status:** N1–N5 built on `Dev` (uncommitted); lab checks outstanding. N6 (release) left.

Panopticon already does the "see it and contain it" half of network access
control: discovery from several sources, SNMP location of each device's
switch port, port disable/quarantine with automatic revert, an ordered
auto-enforcement policy (off / simulate / active), and an embedded RADIUS
server for MAC Authentication Bypass (MAB) with VLAN assignment.

What it lacks, measured against a dedicated NAC such as PacketFence, is the
identity half (802.1X logins, device fingerprinting, a registration portal)
and any link between Panopticon and the rest of Abyssal Arsenal's security
arsenals. That link is the cheapest gap to close and the one a NAC without
host agents can't match, so it comes first.

## Order of work

One milestone at a time on `Dev`, each finished and checked before the next.

| # | Milestone | Size | Agent change? |
| --- | --- | --- | --- |
| N1 | Security signals drive enforcement (Scourge, Thanatos, Cadavault → policy) | Medium | No |

## N1. Security signals drive enforcement

Today a policy rule fires on a device's trust state only (`untrusted`, or
`new_unknown`). Abyssal Arsenal already knows much more about a device than
that, it just doesn't tell Panopticon:

- **Scourge** caches Suricata alerts with the flow's source address
  (`scourge_alerts.src_ip`).
- **Thanatos** stores security events per managed host, with a severity and
  an analyst lifecycle (`open` → acknowledged / resolved / suppressed).
- **Cadavault** stores each host's posture runs and a 0–100 score
  (`posture_runs.score`).

### Decisions

| Question | Decision |
| --- | --- |
| How does a Thanatos event or posture run (keyed by host) find its network device? | A stored link, **`panopticon_devices.host_id`**, set whenever a managed host's agent reports the address as one of its own interfaces (on every agent connect, after each discovery scan, and on the passive refresh for the control plane's server). Cleared when the device's MAC changes (a DHCP address now belongs to someone else). `hosts.last_seen_ip` is used as a fallback only, because it's the address the control plane *sees*, which is wrong for any agent behind NAT and for the control plane's own server (its agent reaches the container through Docker). |
| How does a Scourge alert find its device? | By **source address** (`src_ip` = the device's IP). Never by destination: the destination of an inbound attack is the victim, and quarantining victims is the wrong response. Alerts are already deduplicated per line, so one noisy signature doesn't count twice. |
| What counts as a signal? | Per rule: Scourge alerts and Thanatos events at or above a **minimum severity** (default `high`) within a lookback window (setting `panopticon.auto_enforce_signal_window_minutes`, default 60). Thanatos events only while still **`open`**, so an analyst acknowledging or resolving the event is the way to stand a rule down. Posture: the host's **latest** run scores **below** a per-rule threshold (default 60). |
| Can a signal quarantine the control plane? | **No.** Any device linked to the control-plane host (or at its `last_seen_ip`) is never auto-enforced, by any rule. If it were, the control plane would lose the very switch access it needs to undo the action. Manual enforcement stays possible, with the operator choosing. |
| What about uplinks? | The SNMP poll locates a MAC on whichever port the switch learned it on, which for a device on another switch is the uplink. Auto-enforcing an uplink cuts off everything behind it. The policy sweep therefore skips a port that **has a neighbor that is another polled switch** (LLDP/CDP), or that has **more located devices than `panopticon.auto_enforce_max_devices_per_port`** (default 4: a phone, a PC and some slack). Both guards apply to every rule, including the existing trust-state ones. |
| Why does a port get enforced? | The enforcement reason names the rule and the signal, e.g. `Auto-enforced by policy rule "Quarantine IDS hits": Scourge high alert "ET MALWARE ..."`, so the audit log and the enforcement history say why. |
| Is any of this automatic out of the box? | No. New triggers are only new rule options. The engine stays `off` until an admin sets it to `simulate` (log only) or `active`, and every M3 gate (global kill switch, per-switch opt-in) still applies. |

- [x] Link devices to hosts from agents' own interface addresses (connect, scan, passive refresh); clear the link when a device's MAC changes.
- [x] Triggers `ids_alert`, `security_event`, `posture_failing`, with per-rule thresholds; settings for the signal window and per-port device limit.

## N2. RADIUS CoA and Disconnect

Today a change of trust state or a quarantine reaches a RADIUS-admitted
device only when it next authenticates, or when an SNMP port action bounces
it. RFC 5176 lets the server push the change.

### Decisions

| Question | Decision |
| --- | --- |
| Which request? | Per NAS client (`coa_mode`): **off** (the default for existing clients, so upgrading changes nothing), **Disconnect** (RFC 5176 Disconnect-Request: the session ends and the device re-authenticates; supported almost everywhere, the default for new clients), or **Cisco reauthenticate** (CoA-Request with `Cisco-AVPair = subscriber:command=reauthenticate`: authorization re-runs without dropping link). A VLAN pushed inside a CoA-Request is left out: vendor support is patchy, and re-authentication gets the same result through the normal decision. |
| How is the session identified? | NAS-IP-Address plus **Acct-Session-Id**, the NAS's own handle. Calling-Station-Id (`AA-BB-CC-DD-EE-FF`) only when there's no session id, because RFC 5176 has a NAS NAK a request whose identifying attributes don't all match, and NASes format MACs differently. Sessions come from accounting, so a NAS has to send accounting for CoA to have anything to target. |
| When is it sent? | When a device's **trust state changes** (its open sessions); when a **quarantine is applied to or released from a port** (sessions of every device located there), whether by an operator, a policy rule or the revert sweep; and from a **Reauthorize** button on each active session. Not for a port *disable*: the link goes down, and comes back up re-authenticating on its own. |
| What stops re-authentication undoing a quarantine? | The RADIUS decision now honors **enforcement in effect on the device's port**: quarantine → the quarantine VLAN (reject if none is configured), disable → reject, whatever the device's trust. Before this, an SNMP quarantine on a MAB port was silently overridden by the RADIUS-assigned VLAN at the next authentication; CoA would have made that immediate. |
| What counts as a result? | Only a reply that verifies against the request (its id and Response Authenticator under the NAS secret). Up to 3 tries, 2 s apart. The result (ACK, NAK with its Error-Cause, no response, not sent) is stored on the session and audited as `NETWORK_RADIUS_REAUTHORIZED`. An acknowledged Disconnect, or a NAK with Session-Context-Not-Found, closes the session record. |
| Do the N1 signals reach RADIUS? | Through enforcement: a signal rule that quarantines a port triggers the CoA, and the re-authenticating device lands on the quarantine VLAN. A RADIUS-only deployment (no SNMP write access to the switch) was left for later, and is now covered by **enforcement through RADIUS** (below). |

- [x] Migration 0058: client `coa_mode` + `coa_port`; session `last_coa_at` + `last_coa_result`.
- [x] Sender (`panopticon_coa.rs`): per session, MAC (max 5 open sessions) and port; background for automatic triggers.

## N3. Automatic device classification

Device type was set by hand only; the MAC vendor was the only automatic hint.

### Decisions

| Question | Decision |
| --- | --- |
| Where do DHCP fingerprints come from? | The **ARP listener's existing capture** also parses DHCP client packets (DISCOVER/REQUEST/INFORM): the client MAC from `chaddr` (so relayed packets still name the client), option 55, option 60, option 12. No new capture, capability or setting. It sees DHCP broadcast on its segment, and DHCP **relayed to the control plane**: add it as an extra `ip helper-address` on client VLANs, the way PacketFence does it; behind Docker's bridge network, also publish UDP 67 (commented in `docker-compose.yml`, because it clashes with a DHCP server on the same host). |
| What decides a type? | A pure, tested rule set (`abyssal_core::classify`) weighing: DHCP vendor class, DHCP parameter list, open ports from discovery, MAC vendor, hostname patterns, and the OS a managed host's agent reports. Each rule adds a weight; the best type wins; confidence reflects both its score and its lead over the runner-up, so conflicting evidence (a Cisco MAC running SIP) comes out low. Every rule that fired is shown as a reason. |
| Is it applied automatically? | Only when **`panopticon.auto_classify_enabled`** is on (off by default), every 10 minutes, at **medium confidence or better**, to devices still **Unknown or classified by the classifier itself**. A new `device_type_auto` flag records that; a person choosing any other type clears it, and the UPDATE re-checks it so a classification made since the sweep read the device is never overwritten. Inventory shows automatic types as "(auto)". |
| What does a person see? | The classify page shows the suggestion, OS guess, confidence and reasons, plus the raw DHCP fingerprint. For an unclassified device it preselects a medium-or-better suggestion, so saving accepts it. |
| Changed from the plan | **nmap OS detection (`-O`) is left out**: it needs raw-socket scanning as root, and discovery deliberately runs unprivileged (`-sT`); open ports, which discovery already records, carry most of the same signal. **The fingerprint table isn't editable** yet: the rules are code with tests, and a wrong automatic type is corrected by classifying the device by hand, which sticks. |

### Tasks

- [x] `abyssal_core::classify`: evidence, weights, confidence, reasons, OS family; 10 tests.
- [x] DHCP parsing in the capture loop (bounds-checked, printable text only); tests including truncation at every length.
- [x] Migration 0059: `panopticon_dhcp_fingerprints`, `panopticon_devices.device_type_auto`.
- [x] Classification sweep and the guarded `set_auto_type` write; audit as `NETWORK_DEVICE_CLASSIFIED` with `auto: true` and the reasons.
- [x] Classify page suggestion panel and fingerprint; "(auto)" in inventory; Settings toggle.
- [ ] Lab: with the control plane as an extra helper address, a Windows PC, an iPhone, an Android phone and a printer get fingerprints and the expected suggestions.

## N4. 802.1X logins through FreeRADIUS

The embedded server deliberately rejects anything carrying credentials or
EAP. Real 802.1X comes from FreeRADIUS, not a hand-rolled EAP stack.
Setup: `deploy/freeradius/README.md`.

### Decisions

| Question | Decision |
| --- | --- |
| How does FreeRADIUS run? | An optional compose service (`--profile freeradius`, `freeradius/freeradius-server:3.2.7`) in the **app container's network namespace**. It answers on the RADIUS ports the app already publishes, and reaches Panopticon on `127.0.0.1:8080`. When `FREERADIUS_API_TOKEN` is set, the embedded server doesn't start, so they never contend for 1812/1813. |
| Who decides? | FreeRADIUS authenticates; Panopticon decides, over `rlm_rest`: `authorize` for non-EAP requests (MAB, with the embedded server's exact decision, now one shared `decide_for_mac`), `post-auth` after EAP success (the device's VLAN, quarantine or reject by MAC), `accounting` (sessions, so CoA works). |
| Where are NAS clients defined? | Only in Panopticon. FreeRADIUS uses **dynamic clients**: on a NAS's first packet it fetches the secret (`/internal/radius/client`), and ignores a NAS that isn't listed. |
| How is the API protected? | Endpoints exist only with `FREERADIUS_API_TOKEN` (32+ characters), answer only **loopback** connections (Caddy and everything else arrive from another address), and require HTTP Basic `freeradius:<token>`, compared in constant time. Reply values are sent literally (`do_xlat: false`), so a NAS name or secret containing `%{...}` can't be expanded by FreeRADIUS. Passwords are stripped before FreeRADIUS calls the API. |
| Which EAP methods? | **EAP-TLS** with the operator's CA (`deploy/freeradius/certs`). **PEAP/MSCHAPv2 against AD** was planned but is left out: it needs FreeRADIUS joined to the domain with Samba/winbind, which the official image lacks. It's a follow-up if needed; EAP-TLS is the recommended method anyway. |
| What fails how? | A failed or slow API call rejects (fail closed). During a backup restore, new logins are rejected. An unknown NAS is ignored. |

### Tasks

- [x] `crates/web/src/panopticon_freeradius.rs`: the four endpoints, token/loopback gate, `rlm_rest` JSON parsing and replies; unit tests.
- [x] Shared `decide_for_mac` in `panopticon_radius.rs`; embedded server stands down when FreeRADIUS is configured.
- [x] `deploy/freeradius/`: virtual server, REST module instances, EAP-TLS module, dynamic clients; compose service and `FREERADIUS_API_TOKEN`.
- [x] RADIUS page shows FreeRADIUS mode and its last call.
- [x] `deploy/freeradius/test/run.sh` against the real 3.2.7 image: 14 checks including EAP-TLS with `eapol_test` (accept with VLAN and correct MPPE keys, policy reject, untrusted certificate). It found and fixed a real bug: the `eap` module returns `updated` mid-conversation, which fell through to the MAB check.

## N5. Registration and guest portal

Guest access, PacketFence style: Panopticon runs DHCP, captive DNS and the
portal on the registration VLAN itself (owner's choice, 2026-11-12). Setup:
`deploy/registration/README.md`.

### Decisions

| Question | Decision |
| --- | --- |
| How does a device get there? | A new RADIUS unknown-device action, **Registration portal**: an unknown device without an approved, unexpired registration goes to the **registration VLAN** (`panopticon.portal_vlan`; unset = reject, fail closed), an approved one to the **guest VLAN**. Classified devices keep their treatment, enforcement still wins, and a device that **passed 802.1X** (FreeRADIUS) is admitted plainly: the portal is for devices that can't authenticate. |
| DHCP and DNS | A new crate, `abyssal-portal-net` (no database or web code): a DHCP server (one pool, short leases, Panopticon as router and DNS, the portal URL as RFC 8910 option 114, in-memory leases, relayed requests ignored) and a captive DNS responder (every A question gets the portal, 15 s TTL; AAAA gets nothing). Both are **bound to the registration interface** (`SO_BINDTODEVICE`). DHCP requests also feed N3's fingerprints. |
| The portal | A **separate web server** on the portal address, port 80, serving only `/register`; everything else redirects there, which triggers OS captive sign-in sheets. Plain HTTP, so it never asks for a password. The guest is identified by their **DHCP lease** (requester address → leased MAC). |
| The admin UI | A middleware on the main router answers 404 to anything from the registration subnet: guests can reach the container's address there. |
| Approval | **Sponsor** (default: staff approve, deny or revoke on the Registration portal page; the guest's page refreshes itself) or **self-service** (accepting the terms approves). Approvals last `access_hours` (default 24). Approve and revoke send a CoA (N2); an expiry sweep (1 min) expires lapsed approvals and re-authorizes them. A **denial sticks** (a refused device can't refill the queue), and staff can still approve it later. |
| Docker | The app reaches the VLAN through an opt-in compose override (`deploy/registration/docker-compose.registration.yml`): a **macvlan** network on `<nic>.<vlan>`, marked `internal`, so it's never the container's route. The binary gains `cap_net_bind_service` (ports 53/67/80) alongside `cap_net_raw`. |
| Not in N5 | Login with AD credentials on the portal (would need HTTPS with a certificate guests trust), email/SMS sponsor notifications, DHCP lease persistence across restarts (leases are short), IPv6 on the registration VLAN. |

## Enforcement through RADIUS (closes N2's RADIUS-only gap)

Port enforcement needs SNMP write access and the device located on a port.
Where RADIUS controls a device's access instead, Panopticon now enforces the
**device**: no switch write at all.

### Decisions

| Question | Decision |
| --- | --- |
| What is it? | A **device action** (`panopticon_device_enforcements`, migration 0061), held against the MAC: `quarantine` (the RADIUS decision assigns the quarantine VLAN) or `disable` (the RADIUS decision rejects). The RADIUS decision checks a port action first, then a device action; a CoA applies it, and another lifts it on release or expiry. Without CoA on the NAS, it applies at the device's next login. |
| Why a separate table? | Port actions carry switch, ifIndex and snapshotted SNMP state that the dashboard, revert and SNMP code all rely on. A device action has none of that and can't fail to apply or revert, so it's two states (active, lifted) in its own table, reusing the same kinds. |
| When does the policy engine use it? | It now considers every recent device with a MAC, not only located ones. A match tries the **port** first, exactly as before. If the port isn't available -- not located, an uplink, ifIndex unresolved, or SNMP enforcement not enabled for that switch -- it uses a **device action** when the device has an **open RADIUS session** (proof RADIUS controls its access). A device seen behind an uplink can now be enforced: the port guard still refuses the uplink, but a device action affects only that device. |
| Gates | The global kill switch, Simulate mode (logs which path it would take), one action in effect per device (also enforced in the INSERT), the post-action cooldown, a configured quarantine VLAN for quarantine, and never the control plane's own server. |
| By hand | Classify page: "Enforce through RADIUS" (quarantine or block, auto-revert, reason; warns when the device has no open RADIUS session). Enforcement dashboard: a device-actions section with Release and Make permanent, and recent history. Audited as `NETWORK_DEVICE_ENFORCED` / `NETWORK_DEVICE_RELEASED`. |

### Tasks

- [x] Migration 0061, model, repo (guarded create, cooldown, due list, race-safe release).
- [x] RADIUS decision honors device actions; apply/release with CoA and audit; expiry in the revert sweep.
- [x] Policy engine: all recent devices, port first, RADIUS fallback; pure path checks tested.
- [x] Classify-page card and enforcement-dashboard section.
- [x] SQL verified on a throwaway MariaDB.
- [ ] Lab: on a switch with no SNMP write access, an untrusted-device rule quarantines a MAB device through RADIUS (CoA), and the revert lifts it.
