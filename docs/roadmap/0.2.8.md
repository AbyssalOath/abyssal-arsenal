# 0.2.8 plan: Panopticon NAC, identity and policy

**Status:** P1–P4 built; released as 0.2.8 (P5). Lab checks below still open.

0.2.7 gave Panopticon the pieces of a NAC (MAB, 802.1X through FreeRADIUS,
CoA, classification, a guest portal), and PEAP against Active Directory
followed it. Every decision still comes down to one question asked of the
device's **MAC**: accept with a VLAN, or reject
(`panopticon_radius::Decision`). Compared with PacketFence, that's what holds
it back most:

- It doesn't matter **who** logged in, only which device.
- The only outcome besides reject is a **VLAN**. There are no roles or ACLs,
  so "quarantined, but can still reach WSUS" needs its own VLAN.
- What Abyssal Arsenal knows about a host's **health** (Cadavault posture,
  Thanatos events, Scourge alerts) only acts after the fact, through the
  policy engine, never at login.
- A NAS without CoA keeps a session's decision **until it reconnects**.

0.2.8 closes those four, in that order. Each phase changes the decision
path, so they ship together.

## Order of work

One phase at a time on `Dev`, each finished and checked before the next.

| # | Phase | Size | Agent change? |
| --- | --- | --- | --- |
| P1 | VLAN by AD group (identity-based VLAN) | Medium | No |
| P2 | Roles and ACLs, not just VLANs | Medium | No |
| P3 | Posture and security signals at login | Medium | No |
| P4 | Session-Timeout and periodic re-authentication | Small | No |
| P5 | Release: version, CHANGELOG, `Dev` → `main`, tag | Small | - |

Everything new is off until configured: with no group rules, roles, posture
checks or timeouts set, every decision is exactly what 0.2.7 gives.

## P1. VLAN by AD group

PEAP now knows the user, but the VLAN still comes from the device. P1 lets
an AD group choose it: staff to VLAN 20, Finance to VLAN 30, computers to
VLAN 40.

### Decisions

| Question | Decision |
| --- | --- |
| What is a rule? | **AD group → VLAN**, in an ordered list on the RADIUS page (`panopticon_radius_group_rules`, migration 0062). The **first rule (lowest order) whose group the login is in** wins. A group is written `DOMAIN\Group` or plain `Group` (any domain), matched case-insensitively, nested membership included. |
| Who does it apply to? | Logins that **passed PEAP** against AD: users and computers (`host/...`), each with their own groups (a computer is in `Domain Computers`, say). Not MAB (no identity), and not EAP-TLS yet (certificate → AD account mapping is a follow-up). |
| What does it override? | Only where the device would be admitted anyway. Order: **port or device enforcement** (quarantine/disable) > **Untrusted** (quarantine/reject) > **group rule** > the trusted VLAN or the unknown-device action. An unknown device that logged in with AD gets its group's VLAN under *Accept*, *Guest VLAN* and *Registration portal*, but *Reject* still rejects: classifying it is how an admin lets it in. So a group rule can never take a quarantined or untrusted device out of quarantine. |
| How do the groups get to Panopticon? | FreeRADIUS looks them up with **winbind**, inside the PEAP tunnel, right after the password check. FreeRADIUS truncates a program's output at 2047 characters (measured on 3.2.7), and a user can be in hundreds of groups. So it first fetches the rule groups from Panopticon (`GET /internal/radius/group-names`), a helper (`abyssal-ad-groups`) checks the login's membership (`wbinfo --user-sids`, nested included, one `--sid-to-name` per group because the batch lookup loses the domain) against **only those**, and the matching ones reach the outer `post-auth` call as `Abyssal-AD-Groups`. |
| Can it be spoofed? | `Abyssal-AD-Groups` and `Abyssal-AD-Group-Candidates` are **internal attributes** (`deploy/freeradius/image/dictionary.abyssal`, numbers in FreeRADIUS's internal range): a NAS or client can't send them. The helper gets the login and the candidates as environment variables (FreeRADIUS backslash-escapes `;` and other characters in command-line arguments), no shell is involved, and the login is the one the domain controller just accepted. The API is loopback + token, as before. |
| What if the lookup fails? | winbind down, the user's groups unreadable, or Panopticon's group list unavailable: no groups, so the device gets its **non-group** decision. That's never more access than a group rule would give, because group rules only choose among admitting outcomes. |
| When do rule changes apply? | At each device's next login. No automatic CoA for rule edits (it would re-authenticate every PEAP session at once); the Reauthorize button on a session applies a change now. |
| What's recorded? | Rule changes are audited (`CONFIGURATION_CHANGED`). Each 802.1X decision is logged with the identity, the groups that matched and the rule that won. |

- [x] Migration 0062 `panopticon_radius_group_rules`; model and repo (list, create, delete).
- [x] Pure rule matching (`DOMAIN\Group` or `Group`, case-insensitive, order) and `decide()` taking the group VLAN; tests for precedence over trust, enforcement, untrusted and every unknown action.
- [x] `GET /internal/radius/group-names`; `post-auth` reads `Abyssal-AD-Groups`; decision log line.
- [x] RADIUS page: group rule table, add and delete, with validation (no `;`, no control characters, 256 characters max, VLAN 1–4094).
- [x] FreeRADIUS: internal dictionary, `abyssal-ad-groups` helper, `abyssal_groups` REST call and `abyssal_ad_groups` exec instance in the inner tunnel, groups passed to the outer post-auth.

- A group rule that **rejects** (use `AD_REQUIRE_GROUP` to limit who can log in at all).
- Groups shown on the sessions table.

## P2. Roles and ACLs, not just VLANs

A decision could only be a VLAN or a reject. P2 adds a **role**: the name of
an ACL or user role the NAS already has, so a device can be restricted on
its VLAN instead of moved off it.

### Decisions

| Question | Decision |
| --- | --- |
| How is a role sent? | Per **NAS client**, a *role attribute* (migration 0063): **None** (the default, so existing clients' replies don't change), **Filter-Id** (RFC 2865 attribute 11: Cisco IOS named ACLs written `NAME.in`, Juniper, HPE and most others), or **Aruba-User-Role** (vendor 14823, type 1: Aruba controllers and AOS-CX/AOS-S). Defining the ACL or role stays on the NAS; Panopticon only names it. A Cisco ISE-style downloadable ACL (the server serving ACL contents) is left out. |
| Where are roles set? | One per **outcome** on the RADIUS page (settings): trusted, quarantine, unknown (admitted), guest (guest VLAN and approved registrations), registration. And per **AD group rule** (P1), whose VLAN can now be blank when it sets a role. |
| Which role wins? | The outcome's role, except where an AD group rule applies (same places as its VLAN): there the rule's role, if it has one. A reject never carries a role. Port/device quarantine carries the quarantine role. |
| Quarantine without a VLAN? | Allowed **only on a NAS with a role attribute**: the device keeps its VLAN, restricted by the quarantine role (WSUS and AV reachable, say). On a NAS without one, quarantine without a VLAN still **rejects**, because that NAS would ignore the role and admit the device unrestricted. That's why the decision now knows which NAS is asking. |
| How does the FreeRADIUS path know the NAS? | `mab` and `post-auth` get `?src=%{Packet-Src-IP-Address}`, as accounting already did, then NAS-IP-Address; matched against the enabled NAS clients. No match: no role, and no role-only quarantine (fail closed). |
| What's allowed in a role name? | 1–64 characters of letters, digits and `_ - . :` (`validate_role_name`), checked on save and again when read, so nothing else ever reaches a NAS. |

### Tasks

- [x] Migration 0063: `role_attribute` per NAS client; `role` per group rule (VLAN 0 = keep the device's).
- [x] `RoleAttribute`, `validate_role_name`; role settings per outcome.
- [x] `decide_full` returns a role; role-only quarantine only where the NAS applies roles; tests for every outcome, group roles, and the fail-closed cases.
- [x] Embedded server: `Filter-Id` and the Aruba VSA (`radius::role_attributes`, byte-level test).
- [x] FreeRADIUS API: NAS from `?src=` / NAS-IP-Address, `reply:Filter-Id` / `reply:Aruba-User-Role`; the decision log names the role sent.
- [x] RADIUS page: role per outcome, role attribute per NAS client (and on add), role per group rule.
- [x] `deploy/freeradius/test/run.sh`: Filter-Id on a MAB Accept and Aruba-User-Role on an EAP-TLS Accept reach the NAS through the real FreeRADIUS; the NAS address reaches Panopticon.
- [x] Migration on MariaDB 11; the real app end to end: role per NAS, no role for an unknown NAS, role-only quarantine on a role NAS and reject elsewhere, a role-only group rule.

## P3. Posture and security signals at login

What Cadavault, Thanatos and Scourge know about a machine only acted after
the fact, through the policy engine. P3 checks the same signals at every
login, so a failing machine never gets onto its normal VLAN.

### Decisions

| Question | Decision |
| --- | --- |
| What's checked? | The policy engine's three signals (0.2.7 N1), each off until set on the RADIUS page: the latest **Cadavault posture score** below a threshold (1–100), an **open Thanatos event** at or above a severity, a **Scourge alert** from the device's address at or above a severity. Events and alerts count within the policy engine's signal window (`panopticon.auto_enforce_signal_window_minutes`, default 60). |
| Which devices? | Devices in the inventory. Posture and Thanatos need the device's managed host: its link (`panopticon_devices.host_id`), else an active host last seen at its address, as in the policy engine. Scourge goes by the device's address. A MAC not in the inventory has no signals. |
| What happens? | Each signal has its own outcome, **quarantine** (the quarantine VLAN and role, as for an untrusted device; role-only on a role NAS, else reject, as in P2) or **reject**. Several fire: the strictest wins (reject over quarantine), then the first in order posture, Thanatos, Scourge; the log names it. |
| Where in the decision? | Below port and device enforcement (not even read under it), above everything else. A signal only tightens: it turns an admitting outcome into quarantine or a reject, never a reject into anything else. An AD group rule's VLAN doesn't get a quarantined login out of quarantine. |
| The control plane? | Never restricted by a signal, as the policy engine never enforces it: its own server (host flagged control plane, or an active control-plane host at the device's address) would lose the access it needs to undo it. |
| Fail open or closed? | A database error reading a signal: that signal is skipped and **logged at error level**; the login is decided as without it. The signals only add restrictions, and a database outage already fails logins in other ways. |
| Leaving quarantine | The next login after remediation (a new posture run, the event resolved, the alert out of the window) is decided afresh. Getting that login to happen: CoA (re-authenticate on the RADIUS page), the switch's own re-auth timer, or P4. |
| Unique to Abyssal Arsenal | PacketFence needs third-party agents or syslog parsing for this; here it's the arsenals' own data. |

### Tasks

- [x] Settings `panopticon.radius_signal_{posture_below,posture_action,event_min_severity,event_action,ids_min_severity,ids_action}`; the window reused from N1.
- [x] Per-device lookups in `repo::panopticon_signals` (`host_for_device`, `is_control_plane_ip`, `latest_posture_score`; `top_open_event` and `top_ids_alert` reused), read only when a signal is on and no enforcement applies.
- [x] `decide_full` takes the signal; tests for tightening every admitting outcome, never loosening a reject, enforcement first, role-only quarantine per NAS, strictest-then-first.
- [x] RADIUS page section "Security signals at login" (`POST /arsenals/panopticon/radius/signals`, audited as `panopticon.radius_signals`); the decision log (embedded server, FreeRADIUS MAB and post-auth) names the signal.
- [x] The real app on MariaDB 11, end to end: posture below threshold on a linked host → quarantine VLAN and role (MAB and post-auth); open Thanatos event on a host found by address → reject; Scourge alert → quarantine; control-plane host with failing posture → admitted; remediation (new posture run, event resolved) → back to the trusted VLAN; posture table unreadable → logged, admitted as without it.
- [ ] Lab: a host whose posture drops below the threshold lands in quarantine at its next 802.1X login, and leaves it after remediation (P4 or CoA).

## P4. Session-Timeout and periodic re-authentication

A NAS without CoA (or with CoA blocked) kept a session's decision until the
device reconnected, so a trust change, a lifted quarantine or a fixed
posture (P3) didn't reach it. P4 has the NAS ask again on a timer.

### Decisions

| Question | Decision |
| --- | --- |
| What's sent? | `Session-Timeout` (seconds) with `Termination-Action = RADIUS-Request` on an Accept: at the timeout the NAS re-authenticates the session without dropping the link. Never on a reject. Both servers (embedded: RFC 2865 attributes 27 and 29; FreeRADIUS: `reply:Session-Timeout`, `reply:Termination-Action`). |
| How long? | Per outcome, in minutes, on the RADIUS page: trusted, quarantine, unknown (admitted), guest, registration. **Default 0 = none**, so 0.2.7 replies don't change. Otherwise 5 minutes to 1 week (floor so a NAS isn't kept busy; checked on save, capped again when read). Suggested on the page: quarantine and registration 5–15, trusted 480–1440. |
| Which outcome is which? | As for roles (P2): port/device quarantine and P3's quarantine signal use the quarantine timeout; an 802.1X-authenticated unclassified device under the portal uses the unknown one. |
| Guests | An approved registration's session ends no later than the registration: `min(guest timeout, time left)`, with a 60-second floor so an almost-expired one doesn't loop. Only when a guest timeout is set (off until configured, like everything else). |
| Per NAS? | No: one value per outcome. A NAS that ignores Session-Timeout is unaffected; Cisco needs `authentication periodic` and `authentication timer reauthenticate server` on the port (said on the page). |

### Tasks

- [x] Settings `panopticon.radius_timeout_{trusted,quarantine,unknown,guest,registration}_minutes`; RADIUS page fieldset, validated (0 or 5–10080).
- [x] `decide_full` returns `session_timeout`; tests for every outcome, quarantine via enforcement and signals, none on reject or when unset, registration time left and the floor.
- [x] Embedded server: `radius::session_timeout_attributes` (byte-level test). FreeRADIUS API: `insert_session_timeout` (rlm_rest names test). The decision log shows the timeout.
- [x] `deploy/freeradius/test/run.sh`: Session-Timeout and Termination-Action = RADIUS-Request reach the NAS through the real FreeRADIUS (20/20).
- [x] The real app on MariaDB 11: no timeouts set → none sent; with them, trusted 28800, quarantine 600, registration 300, guest 3600, a registration with 20 minutes left 1197; PEAP post-auth too.
- [ ] Lab: a NAS with CoA off picks up a trust change at the timeout.

## Backlog (after 0.2.8)

Gaps against PacketFence not in 0.2.8, roughly by value.

The next plan, [0.2.9.md](0.2.9.md), takes B1, B6 and B7 and carries the rest.

| # | Item | Notes |
| --- | --- | --- |
| B1 | **SNMP traps** for faster detection | A listener on UDP 162 for link-up/down and MAC-notification traps, triggering an immediate poll of that port. Near-instant detection and policy on switches without RADIUS. |
| B2 | **Editable fingerprint rules** | An admin table (DHCP option 55/60, vendor, hostname → type and OS) on top of `abyssal_core::classify`. Fingerbank's API needs a license key and sends data out: an owner decision. |
| B3 | **Randomized (private) MAC addresses** | Recognize locally administered MACs; shorter registrations and an inventory hint for them; for 802.1X, tie the device to the username. |
| B4 | **Portal improvements** | AD login on the portal (needs HTTPS with a trusted certificate), email notification to sponsors, DHCP leases persisted across restarts, IPv6 on the registration VLAN. |
| B5 | **Self-service certificate enrollment** | Portal-driven EAP-TLS onboarding for BYOD (SCEP or an enrollment page). Large; only if BYOD matters. |
| B6 | **Simulate results in the UI** | A "would have enforced" table on the policy page instead of the server log. |
| B7 | **Rogue DHCP server detection** | The ARP listener already parses DHCP: alert on an OFFER from a server that isn't on an allowed list. |
| B8 | **EAP-TLS → AD group mapping** | Map the certificate's UPN or SAN to an AD account, so P1's group rules work for EAP-TLS too. |
| B9 | **Firewall user mapping** | User ↔ IP to Palo Alto / FortiGate User-ID. Only if one of those is in use. |
| B10 | **High availability** | A standby control plane. Large; meanwhile, a secondary RADIUS server on the NAS pointing at a standby. |

Not planned: inline enforcement (Panopticon as the gateway; VLANs and ACLs
cover the need), EAP-TTLS and PAP against AD (little demand once PEAP and
EAP-TLS exist).
