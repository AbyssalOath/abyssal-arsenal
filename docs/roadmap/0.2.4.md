# 0.2.4 plan

0.2.4 has two features:

1. A check-by-check security posture report for Cadavault, in the style of
   Wazuh's SCA.
2. Folding deployment tokens into the agent install token (AAT) model.

Both were held back from 0.2.3 to keep that release's test surface to what
was already built.

---

## 1. Cadavault: check-by-check posture report

### Today

`/arsenals/cadavault/<host>/posture` shows six category rows: firewall,
SSH, kernel (sysctl), account policy, MAC, and automatic updates. Each row
has a pass/warn/fail status and a one-line summary, and the six roll up into
a weighted score with suggested next steps. That's useful at a glance, but
it doesn't say *which* setting failed or *how to fix it*, and Windows gets
far less than Linux.

### Goal

A report like Wazuh's Security Configuration Assessment. Every individual
check is listed with:

- a stable ID, such as `AA-LNX-SSH-003` or `AA-WIN-SMB-001`;
- a title;
- a rationale (why it matters);
- the evidence: what was actually found on the host;
- a status: passed, failed, or not applicable (with the reason);
- a remediation: what to change, and a command or policy path where one is
  safe to show;
- optional references: CIS benchmark section and MITRE ATT&CK technique.

The summary above the list shows passed / failed / not applicable, the
score, and the change since the previous run.

### Design

- **A check catalog, as data, in a new crate (`abyssal-posture`).** Each
  check holds its ID, platform (`linux`, `windows`, or both), title,
  rationale, remediation text and references, plus a *rule* that decides
  pass or fail from facts the agent reports. The rules live control-plane
  side, so improving a check needs no agent update.
- **One fact-gathering agent operation, `PostureFacts`** (a new protocol
  version). It's read-only and runs concurrently, and returns structured
  key/value facts:
  - **Linux:** the effective `sshd -T` config, the relevant `sysctl -a`
    keys, `login.defs` and PAM password policy, firewall state, SELinux or
    AppArmor mode, update-timer state, world-writable and SUID file counts
    in system paths, mount options for `/tmp` and `/dev/shm`, enabled
    legacy services, and auditd rules present.
  - **Windows:** `secedit /export` (password and lockout policy, user
    rights), `auditpol /get`, the SMB server config (SMBv1, signing),
    firewall profiles, Defender state (real-time protection, signature age,
    tamper protection), BitLocker status, UAC and LSA protection (RunAsPPL)
    registry values, the RDP NLA setting, LLMNR / NetBIOS-over-TCP, guest
    and administrator account state, and the Windows Update service and
    last install.

  The existing Cadavault reads (`SshdConfigAudit`, `SysctlSecurityPosture`
  and the rest) stay as they are for their own buttons.
- **A first catalog of about 45 Linux and 35 Windows checks**, chosen for
  value with no false positives over breadth. For example: SSH root login,
  password auth, MaxAuthTries, X11 forwarding; ASLR, `rp_filter`, ICMP
  redirects; firewall on with default-deny inbound; password
  length/age/lockout; SMBv1 off; SMB signing required; NLA on;
  Defender real-time on with signatures under 3 days old; LSA protection;
  LLMNR off; the audit policy for logon/process-creation/account changes.
- **Remediation is text, never executed.** Commands are shown to copy and
  are marked as needing a review before being run. A few with existing safe
  Cadavault actions (SSH hardening, firewall allow/enable) link to them, so
  "fix" goes through the normal confirm, permission and audit path. On the
  control plane's own host, fixes the guard would refuse are shown as such.
- **Results are stored** (`posture_runs`, `posture_results`: run ID, host,
  check ID, status, evidence, time). That gives history, the "changed since
  last run" line, and a fleet view.
- **Scheduling:** optionally once a day per host (a setting, off by
  default), alongside the on-demand button.

### UI

- **The host report:** a summary bar (score, passed/failed/NA, change since
  last run), a filter (failed / passed / NA / all, plus search), and
  expandable check rows. Each row shows the status, ID and title; expanded,
  it shows the rationale, evidence and remediation, with a copy button.
- **A fleet view** (`/arsenals/cadavault/posture`): the checks failing on
  the most hosts, each linking to the hosts where it fails. Plus each host's
  score and trend.
- **Export:** CSV of a run, and the existing syslog/SIEM export carries
  failed checks (with `scope=posture`) so they can be alerted on.

### Testing

- Each rule is unit-tested against recorded facts for its pass, fail and NA
  cases: a sample `sshd -T`, `secedit` export and `auditpol` output.
- The `PostureFacts` PowerShell is parsed in CI (the same pattern as the
  Thanatos stream script). Its output is captured once from a real Windows
  host into a fixture.
- End to end on a Linux host and a Windows host. The remediation commands
  get a manual review pass before release.

### Open questions

- Ship CIS references only where the mapping is certain, or leave them out
  of the first cut?
- Should the daily scheduled run alert on a newly failing check, or only
  feed the fleet view?

## 2. Deployment tokens become additional install tokens

### Today

There are two kinds of reusable enrollment secrets:

- **The AAT.** One per control plane, it never expires, and it works with
  the exe and MSI `/install … SERVER= AAT=` switches and the CA-proof
  bootstrap. The "require approval" setting applies to it. Rotating it
  breaks every package that embeds it.
- **Deployment tokens.** Created per rollout, with an expiry, a label, a use
  count and individual revocation. They only work with the generated
  one-liners (which pin the CA fingerprint), not with the exe/MSI switches
  or the CA proof, and approval doesn't apply.

The overlap is large and the differences are surprising.

### Goal

Keep what deployment tokens are good for (expiry, labels, use counts,
revoking one rollout without touching the rest) and drop the second
mechanism. That's CrowdStrike's model: one CID, plus optional installation
tokens.

### Design

- **"Install tokens" on `/admin/hosts`:**
  - **The default token** is today's AAT. It doesn't expire, can be
    rotated, and stays the default in the commands shown.
  - **Additional tokens** have a label, an optional expiry, a use count and
    their own revoke button. They're created with "New install token".
- **Every install token works everywhere the AAT does:**
  - exe `/install` and MSI `AAT=`;
  - `install.ps1`, the Linux one-liner, and SSH deploy;
  - the CA-proof bootstrap (`/api/agent/ca?nonce=`). The proof is keyed on
    the token presented, so the server looks up which token it is.

  It keeps the `AAT1-` format, so agents and packages need no changes.
- **Per-token approval:** each token can require approval or not, with the
  default following today's setting. "Contractor batch: require approval"
  becomes possible.
- **Storage:** additional tokens are encrypted at rest with
  `ENCRYPTION_KEY`, like the AAT, because the CA proof needs the secret. The
  token's hash is kept alongside for lookup, and the token is shown once at
  creation, plus on demand with an audit record, like the AAT today.
- **Migration:** existing deployment tokens keep working until they expire
  or are revoked, and are listed as "legacy (one-liner only)". New ones
  can't be created. The old one-liner path is removed in 0.2.5.
- **Enrollment** records which token enrolled each host (the token ID). The
  host row and the audit trail show it, which also gives the use count.
- **Protocol:** none of this changes the agent, because the token is opaque
  to it. It's all control-plane side.

### UI

- A single "Install tokens" card replaces both the AAT card and the
  deployment-token card. It lists the default token, then additional tokens
  with label, created, expires, uses, approval and actions.
- The per-OS commands (exe, MSI, PowerShell, Linux) take a token picker,
  defaulting to the default token.

### Testing

- Enrolling through every path with an additional token: exe and MSI on
  Windows, the one-liner on Linux, SSH deploy, plus the CA proof.
- An expired token, a revoked token, and per-token approval.
- A rotated default token doesn't affect additional ones, and vice versa.
- A legacy deployment token still enrolls until it expires.

### Open questions

- Should additional tokens be allowed to never expire, or must they always
  have an expiry (which nudges good hygiene)?
- Should the default token be allowed to expire too?
