{% call macros::icon("danger") %} High-risk storage operations

Gates Ossuary's partition/RAID/LVM-create and mkfs -- a wrong device path here destroys a disk instantly.

Gates Ossuary's most dangerous operations -- partition table create/delete, RAID array create/stop, LVM physical volume/volume group/logical volume create and remove, and creating a filesystem. {% call macros::icon("danger") %} Host network isolation

Gates Inquest's full host isolation -- can sever a host's own manageability with no remote fix.

Learn more

Blocks all network traffic except the control plane's own connection. Unlike every other destructive operation this platform dispatches, a wrong edge case here (NAT, a DNS-based control-plane address, a multi-homed host) can sever the agent's own connection back to the control plane with no remote way to undo it -- recovery would need physical or console access to the host. Off by default; this is a second, deliberate layer on top of (not instead of) the type-to-confirm the operation still requires.

Monitoring & Alerts

{% call macros::icon("audit") %} Thanatos background monitoring

Unattended sweep that scans every host's security logs and can raise alerts on its own.

Learn more

A fixed-interval sweep that scans every connected host's security logs, persists what it finds, and can raise correlation alerts on its own -- nobody has to click anything. Off by default: this reads and stores security-log content across your whole fleet automatically once enabled. Manual, admin-triggered scans from the Thanatos page work regardless of this setting; it only controls the unattended sweep.

{% if thanatos_monitoring_enabled %}Enabled{% else %}Disabled{% endif %}
{% call macros::icon("audit") %} Thanatos alert recipients

Who gets notified when Thanatos raises a correlation alert.

Learn more

Comma-separated email addresses, sent through whatever notification provider is configured (SMTP today, set via environment variables). An alert is still recorded and shown on the Thanatos page even with no recipients set -- this only controls whether it's also actively pushed out.

{% call macros::icon("audit") %} Thanatos extra file-integrity paths

Extra files hashed for tampering, on top of the built-in watch-list.

Learn more

Comma- or newline-separated absolute paths, added to (never replacing) the small fixed set Thanatos already hashes on every scan. Each path only applies to hosts of a matching platform -- a Linux path (starting with /) is sent only to Linux hosts, a Windows path (C:\...) only to Windows hosts -- so a mixed fleet's list can freely contain both kinds together.

{% call macros::icon("audit") %} Thanatos correlation & sweep tuning

How sensitive correlation is, and how often the unattended sweep polls.

Learn more

A correlation alert fires when a host logs at least this many high-or-critical security events within the window below -- the window also doubles as that alert's own cooldown, so it won't fire again for the same host until the window has passed. The sweep interval is how often the unattended background sweep polls every connected host when background monitoring (above) is on; a change here takes effect within one old-length interval, not a restart.

{% call macros::icon("scan") %} Panopticon active sweep

Unattended scan that re-runs a discovery scan against a fixed target on a schedule.

Learn more

Every 30 minutes, runs the same nmap discovery scan the Panopticon page's manual scan does, against the target set below, and records what it finds -- nobody has to click anything. Off by default: this sends real scan traffic to a whole target range on its own schedule, which can trip intrusion detection on or near that target. Panopticon's passive neighbor-table refresh (continuous device discovery that never sends traffic) runs regardless of this setting; only the active scan is gated. Manual, admin-triggered scans from the Panopticon page work regardless of this setting either way.

{% if panopticon_sweep_enabled %}Enabled{% else %}Disabled{% endif %}
{% call macros::icon("scan") %} Panopticon sweep target

IP, CIDR range, or hostname the active sweep scans on each run.

Learn more

The active sweep does nothing on a tick where this is empty, even if the toggle above is on -- there's no default target to guess. Scans every port nmap checks by default, same as leaving the port field blank on a manual scan.

{% call macros::icon("network") %} Panopticon mDNS listener

Passive discovery from devices that self-announce over mDNS (*.local).

Learn more

An ordinary UDP multicast socket join on port 5353 -- no elevated privileges needed. Picks up consumer devices (printers, IoT, phones, Macs, Chromecasts) that self-announce a *.local hostname even if they never respond to an active scan. This binds a real socket at startup, so toggling this takes a server restart, not just this save.

{% if panopticon_mdns_enabled %}Enabled{% else %}Disabled{% endif %}
{% call macros::icon("network") %} Panopticon ARP listener

Passive discovery by sniffing raw ARP traffic on a network interface.

Learn more

Requires CAP_NET_RAW (see the Dockerfile/docker-compose.yml) -- a real deviation from every other arsenal here, which all run unprivileged. Behind Docker's default bridge network this only ever sees the Docker bridge's own ARP traffic, not a physical LAN's; host networking (or running the binary directly) is required to see real LAN traffic. This opens a real raw-socket capture at startup, so toggling this or changing the interface below takes a server restart.

{% if panopticon_arp_enabled %}Enabled{% else %}Disabled{% endif %}
{% call macros::icon("network") %} Panopticon ARP interface

Network interface the ARP listener captures on, e.g. eth0.

Learn more

The ARP listener doesn't start at all if this is empty, even if the toggle above is on -- there's no default interface to guess.

{% call macros::icon("network") %} Panopticon bandwidth history

How long to keep per-switch-port bandwidth samples, at each resolution.

Learn more

Raw 5-minute samples come from the same SNMP poll that already reads each switch's MAC/port table -- no separate polling cadence. Hourly and daily are optional rollups computed from raw data once it's old enough; either one set to 0 is fully off -- nothing computed, nothing stored, any existing rows for it deleted -- so a bandwidth graph beyond the raw window then has nothing to show unless the other rollup tier is on. Raw retention has a 2-day floor: the daily rollup needs a full elapsed day of raw data on hand when it runs.
