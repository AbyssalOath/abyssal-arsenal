Abyssal Arsenal is server-rendered HTML/CSS by design (see ARCHITECTURE.md). It is JavaScript-free by default; the one deliberate enhancement is opt-in, per-browser htmx partial refresh for live pages (a vendored, same-origin htmx.min.js loaded only when a viewer turns on "Live updates" with "Partial updates" checked), plus the two progress pages (scan, deploy). With htmx off, live pages fall back to a no-JS <meta http-equiv="refresh">. Every page reuses the components on this page rather than inventing its own button, input, or card styling. If you're adding a new page or module, copy from here instead of writing new CSS.

Live updates. Pages that poll use the shared live_updates_control / refresh_head macros and a .live-region that hx-gets a fragment endpoint. The offered auto-refresh intervals are Off / 5s / 15s / 30s / 60s; the 5s choice only polls at 5s with Partial updates on (the no-JS fallback clamps it to 15s). The set is enforced server-side in dashboard_prefs::REFRESH_CHOICES.

Severity colors

Button color communicates what an action does, not which module it's in. Applied the same way everywhere: Users, Roles, Hosts, Modules, and every arsenal.

view, check, list, filter -- read-only, no side effects
create, update, enable, bring up -- a real mutation, but additive/reversible
delete, remove, bring down, revoke -- always behind a confirm step
the one unclassed default -- sign-in, and other single primary actions on auth pages

Buttons

All four variants share consistent padding, radius, and font-weight, and all define hover, active (press), disabled, and focus-visible states.

Loading spinners are not implemented: this app is JavaScript-free by default (the only scripts are opt-in, vendored, same-origin ones -- htmx for live partial refresh, and a cosmetic easter egg), and a core page must work with scripting off; a true per-click spinner would need script to intercept the submit and swap in an overlay. The closest CSS-only affordance is the :active press-state above (click and hold a button to see it) plus the disabled state on the confirm/results pages that already re-render after a submit completes.

Inputs

Recessed background with an inner shadow so inputs read as "fillable," distinct from cards and buttons, with a visible accent-colored focus ring and legible placeholder contrast.

Results panel

Every arsenal action that produces output (a check, a lookup, a test run) renders into a collapsible <details class="results-panel"> instead of assuming the output appears somewhere obvious. It opens automatically once there's something to show, and has a real empty state before that.

Suggested Next Steps (Contextual Arsenal Workflow Navigation)

When an arsenal's result implies "go investigate this elsewhere" (Cystoolbox's disk usage is critical, a security scan raised an alert, a certificate is expiring soon), the workflow registry (crates/workflows) renders every matching suggestion here -- never auto-navigating, never auto-executing. Deliberately distinct from both the results panel above (what just happened) and an info banner (why you're here): the accent-colored left border marks it as an actionable next step, and its .btn-suggestion outline buttons are never confused with this page's own Read/Write/Destructive buttons. Multiple matches always render together as a button group -- nothing here picks a "best" one for you.

Confirmation patterns

Every destructive action requires a dedicated confirm page (never a bare button). Two strengths, chosen by how easily the action can be undone:

  • Plain confirm -- a single "Confirm" button on its own page. Used for reversible actions: revoke a host (re-enroll undoes it), disable a user, force logout, save role permissions, disable a module.
  • Type-to-confirm -- the confirm page also requires typing the exact hostname/username/target back before the button submits anything. Used for irreversible actions or ones that risk locking out access: delete a user, remove a host, reboot, enable a firewall, bring an interface down, run a network scan.

Both are enforced server-side (require_typed_confirmation / the confirm flag) since there's no JavaScript to gate the submit button client-side -- a mismatch just re-renders the same validation error every other bad input on this app produces.

Elevation status ("Apotheosis")

The same .badge-elevated badge appears everywhere a host's elevation state is shown: the Hosts list, every host-detail page, and the Apotheosis dropdown in the top nav -- so "is this host currently elevated" always looks the same no matter where you're looking from.

Accessibility

Every text/background color pair in both themes was checked against the WCAG AA thresholds (4.5:1 for normal text, 3:1 for large text and UI components) using the real relative-luminance formula, not eyeballed. One real failure was found and fixed: the dark theme's danger button (white text on the bright badge/border red) measured 3.27:1. Buttons now use a separate, darker --danger-btn-bg token so the button passes contrast (5.4:1, 4.8:1 on hover) without dimming the brighter --danger red that badges, borders, and banners rely on for their own legibility against dark surfaces. Disabled controls are exempt from contrast requirements per WCAG 1.4.3 (they're not interactive content), which is why they're dimmed with opacity rather than a separate compliant color pair.
